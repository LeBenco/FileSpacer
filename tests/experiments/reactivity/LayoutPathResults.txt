Content, remaining latency and persistent scrolling, 2026-11-07
==============================================================

Scope
-----
AgentWin10, Windows 10 19045, 5000 files, Debug x64. Hosted and Explorer views
have an 800x400 viewport. These are focused probes, not another complete suite.
The host now uses FS's FWF_NOWEBVIEW and FWF_NOHEADERINALLVIEWS as well as
FWF_AUTOARRANGE. Historical tables lacking those flags remain historical data.

Real Content
------------
Classic FVM_CONTENT reports mode 8, but uses SysListView32 and a tile layout.
The exact VM image's CListViewHost::_SetViewMode maps both mode 6 and mode 8
to native tile view. Screenshots confirm this; the old forced Content row was
neither a reachable FS command nor an actual modern Content view.

FVO_DEFAULT produces real full-width Content rows through DirectUIHWND, as in
Explorer. The existing modern selection and ScrollPattern code works with it.

Observed final composed image, two focused trials, milliseconds:

                         First trial       Focus explicitly seeded at item 7
FS host, classic alias       317.270                       332.199
FS host, real Content         54.191                        61.721
Explorer, real Content        62.985                        41.924

All identities, retained arrays and focus checks pass. Each final-image value
is one observation, with no coalesced frame. These establish comparable latency
on this control, not that either application is generally faster. Content can
reuse the existing modern backend; a future FS command must request that profile.
No Content menu entry is added in this change.

The three remaining investigations
---------------------------------
1. Complete-selection capture in free icons still spends time in native spatial
   enumeration. An indexed-geometry anchor prototype reduced a regular-layout
   capture from 371.919 to 99.172 ms and matched the native anchor identity.
   It is not adopted: the stronger irregular-layout paired run stopped at a
   pointer-parking precondition, before validating the candidate. Its reference
   captures were 560.726 / 548.004 / 542.735 ms. No paired gain is claimed there.
   The final shared-viewport implementation below supersedes this prototype.

2. Arranged Tiles returns from selection restoration in about 30-41 ms, but
   its final image was observed at 302-333 ms, against Explorer's 39-48 ms.
   First changed images at about 47-54 ms already show all visible rows selected;
   the later image adds type/size metadata after a scroll to different rows.
   The original restoration's last-item/anchor detour triggers native timer 4
   at about 250 ms. Matched-image disassembly identifies
   CListViewHost::_OnScrollTimerExpired and its deferred-provider callbacks.

   Removing the anchor entirely gives 85-95 ms, but loses restoration and was
   rejected. Keeping one anchor reveal gives 48.511 ms when no real viewport
   displacement is needed. The stronger displaced-viewport test did not prove
   the required original position; that variant is not delivered as a fix.
   The final viewport-only path below instead restores measured coordinates.
   New selection snapshots now use that shared viewport; the legacy anchor
   protocol remains only for old snapshots and unsupported capture contexts.
   Calling the private scroll-timer callback has not been implemented or tested.

3. First GetSelection(FALSE) in free icons remains about 235-277 ms. A public
   prototype reads each item's geometry once, sorts the cached coordinates,
   rotates the sequence to the focused item and calls SHCreateShellItemArray.
   With focus at item 7 it took 25.917 / 28.083 / 32.240 ms, against native
   252.522 / 246.919 / 277.494 ms in the same trial. Ordered identities match;
   both arrays retain their original contents after native deselection.
   It is not integrated into FS or injected into the Shell's cache. Partial
   selections, grouping and broader variants still need qualification before
   using it in nativeViewSelection. External Shell consumers remain native.

Persistent scrolling: cause and delivered implementation
-------------------------------------------------------
Normal per-folder state had no viewport field. Selection/scroll snapshots were
only consumed by the closed-window-history command, not an ordinary folder open.
Schema 7 adds a nullable scroll column and independent read/update operations.
Existing layout/view/icon blobs are preserved. Updates never create a missing
folder row, do not freeze navigation under a layout lock, and skip identical
bytes. Rekey/reset/deletion/quota semantics remain attached to the folder row.

The dedicated snapshot is 48 bytes, containing mode, icon size and either DPI
and client coordinates, or public ScrollPattern percentages. Classic views use
LVM_GETITEMRECT for item 0 and one LVM_SCROLL delta, on a unique current-process,
current-thread ListView whose mode/count match the COM view. Modern views use
the existing public in-process IScrollProvider. No file enumeration is needed.

The control-composition dependency is optional, not a guaranteed Shell COM
contract. Unsupported/mismatched contexts keep their native position. There is
no new private function, DLL offset, patch or symbol-discovery requirement.
Changed contents/layout/DPI imply best-effort restoration, as agreed.

Visible LVM_SCROLL initially took about 200-300 ms in classic views. Suspending
redraw for the single delta, then resuming it, removes that animation. All 36
native round trips pass across 12 profiles: the seven available FS modes, free
icons, free Tiles, real modern Content and classic List/Details fallback controls.
They check the exact viewport blob, selected identity, logical/keyboard focus,
cancellation, invalid version and truncated input.

Final API-return timings, three samples per profile, milliseconds:
  Classic capture: generally 0.05-0.6; largest final native sample below 1.
  Classic restore: approximately 6-33 (classic Details about 1).
  Modern List/Details/Content restore: approximately 0.4-0.6.
  Modern capture after provider initialization: approximately 0.6-1.1.
  First modern provider access: 82.628 in this run.
These are incremental API timings, not whole-window or composed-image latency.
Complete-selection capture now embeds the same viewport, as described below.

FS captures on close, preserves a View-menu preview's original viewport, and
applies once after presentation, free positions and optional reopen selection.
Refresh and renderer recreation do not replay it. Filtered/provisional state
does not replace the trusted viewport. Ordinary reopen restores both axes and
does not select files.

Shared viewport in selection snapshots (delivered, format 3)
------------------------------------------------------------
The new helper replaces the spatially sorted anchor capture and the last-item /
anchor detour. The 20-byte header is followed by the 48-byte viewport, then the
optional focused PIDL and selected PIDLs. Decoding validates the whole snapshot
before selection changes. Formats 1 and 2 remain readable; capture still uses
the old protocol if the optional viewport capability is unavailable. Explicit
history/transient restoration takes precedence over the ordinary saved viewport.
