Selection collapse and final bounded measurements -- 8 November 2026
==================================================================

Adopted implementation
----------------------
The classic control already sends a global LVN_ITEMCHANGED after clearing
its selection, followed by a single-item notification when an item was clicked.
The slow part was inside the Shell host's handling of that global notification:
about 1.15--1.28 seconds in the isolated 5,000-item control.

Read-only, nonsuspending CDB inspection of the current Explorer process confirms
ExplorerFrame!CSelectionState::_DeselectAll calls RemoveAll on its selection
maps/arrays. The retained adaptation applies that batching principle to the
classic Shell manager; it does not call ExplorerFrame methods or replace the
renderer. The existing qualified manager, callback, notification and cancellation
functions are reused. No new offsets, cache schema or prepared version profiles
were introduced. Existing asynchronous discovery/public fallback remains intact.

ShellViewSelection handles the global deselection after proving the native
registration, zero control selection, matching manager/array, bounded count,
entry layout and writable storage. It releases native subscriptions in one
batch and forwards the original notification. The existing completion
notification then invalidates ordinary selection snapshots and cancels stale
delayed activation, guarded against detachment, destruction and replacement.
The explicit clear operation shares the same entry-purge routine.

FolderWindow no longer preclears background mouse presses. The associated
capability accessor and Debug FS_TEST_CLICK_PRECLEAR switch were removed.
The new input path does not require the optional private index range. That
range remains useful for explicit clearing such as Escape. The implementation
adds no mouse hook, timer, executable-memory write or new private function address.

Public alternatives
-------------------
Four public variants were exercised in the independent prototype: IShellView
clear and IShellFolderView::Select(SFVS_SELECT_NONE) inside the global notice,
and public exclusive selection before release, with/without SetRedraw.
The calls inside the notice were no-ops because the control was already empty;
the pre-release variants retained about 1.2--1.4 seconds of work. None provided
the strong gain. A public entry point benefiting from the private observer is
not a purely public implementation. The true public-only application control
below disables private discovery/capabilities.

The discarded release-hook prototype reached about 37/44 ms for free Icons/
Tiles, but the notification prototype reached about 38/45 ms without changing
input handling. Only the latter approach was adopted.

Explorer and partial-array control
---------------------------------
The final independent Tail benchmark passed 30 exact partial-array rows and
six real Explorer clicks at the same dimensions, filenames and icon sizes:
 build/regression/20261108-201409-e26a8d19cf264747bcb7b51e4a9ea2c2

Explorer click-item medians, three samples: medium 48.040 ms; Tiles 44.990 ms.
Explorer does not implement equivalent free folder placement, so these are
arranged-view comparisons only. The remaining application difference is tens
of milliseconds and every final private application sample is below 200 ms.

First explicit read of 4,999 selected items in a real Shell host, three samples:
                        native API     integrated public reader
 free Icons              359.140 ms           364.450 ms
 free Tiles               41.843 ms            40.706 ms
The integrated reader correctly retains native fallback for partial selections.
These are array-call timings, not complete application/display timings. The
combined selection-change/read clock is logged separately. Explorer may eagerly
prepare its snapshot; no claim is made that its cached-array read is cold.
No partial-array optimization is adopted: these values meet the accepted
500-ms criterion above 1,000 items, without an equivalent Explorer free view.

Earlier Tail attempts rejected an exposed tile subfield as the target. The
final target verifies the icon point and its enclosing list-item identity;
post-click identity is checked independently. These setup failures are retained
in their original run directories, rather than relabelled as application PASS.
