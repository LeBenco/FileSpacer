Native position-dump investigation, 2026-11-07
============================================

Question and scope
------------------
Can a native saved layout replace the expensive application of thousands of free
positions? The probe uses the real Shell in AgentWin10, Windows 10 19045, MSVC
Debug x64/C++14 with CFG and /W4. Production FileSpacer code is unchanged.
Both free medium Icons and free Tiles are exercised in 5000-file fixtures.
No host UI is manipulated. Explorer folders have no equivalent free-position
layout, so arranged Explorer selection timings are not a positioning benchmark.

Existing FS implementation
--------------------------
ShellViewIcons already serializes child identities and coordinates, skips
unchanged coordinates, and sends the remaining positions in one public
IFolderView::SelectAndPositionItems call. Its optional redraw guard suppresses
premature native resumes during that batch. Merely changing the file format to
a larger blob or issuing a single public call is therefore not a new speedup.
A useful native dump would need a different loading/application path.

Public/native-state probe
-------------------------
PositionDumpTests.cpp reuses the independent OrderTransfer host scaffolding.
It compares a stream supplied through IShellBrowser with ordinary native
ExplorerBrowser persistence using SetPropertyBag after Initialize. The stream
site implements the public IShellBrowser/IServiceProvider/ICommDlgBrowser2
interfaces used by FS, plus its existing WM_USER+7 hosting compatibility hook.
That hook is observed Shell hosting behavior, not a public persistence contract.
Service discovery logging is bounded and deduplicated. No private method, raw
object offset, remote memory write, injection or executable patch is used.

A capability check precedes expensive full-layout seeding: two unmistakable
identities, at view indices 0 and 4000, are displaced with DPI-scaled coordinates.
Only those two records are applied through production restoreIconPositions.
All 5000 observed coordinates and identities are captured for comparison after
destroying/recreating the native view. Passing GetItemPosition/SaveViewState
alone cannot qualify a successful restore. The two displaced identities must
actually return to their saved coordinates. Partial natural-layout coincidence
is reported separately and never counted as a restored layout.

Two contrasting ordinary-setting controls check the native persistence route:
SmallIcon/16 and then Details are saved and independently observed after native
view recreation with FVM_AUTO. Both controls pass for both starting modes.
This is same-process view recreation, not a separate-process restart test.
The modes/flags of the position candidate itself are not re-applied on reopen.

Stream qualification limitation
-------------------------------
In this ExplorerBrowser profile the supplied stream is never requested: zero
read/write callbacks and zero saved bytes, despite SaveViewState returning S_OK.
Both stream rows are explicitly UNQUALIFIED, not successful empty snapshots and
not proof that every possible Shell stream would omit positions. No result is
inferred from identical empty A/B buffers. The runner requires completion of all
four arms, both usable native-bag comparisons and both positive-setting controls;
it prints the stream qualification limitation rather than hiding it in PASS.

Read-only SHGetViewStatePropertyBag probes of the named application bag and the
fixture's Shell bag do not expose Mode or IconLayouts (ERROR_FILE_NOT_FOUND).
Because even Mode is absent there, this does not prove the absence of a native
layout blob elsewhere. It proves that these attempted bag lookups do not retrieve
it. No desktop/user bag is modified or reset. Probe state belongs to unique VM
fixtures and unique application bag names.

Internal evidence and remaining opportunity
------------------------------------------
Offline Microsoft-symbol disassembly of the host's shell32 10.0.19041.5678 shows:
- CLegacyViewState::_LoadPositionBlob reads a whole stream into owned storage and
  builds its native record index.
- CLegacyViewState::_SyncPositions then iterates records, resolves each identity
  and calls the native ListView positioning interface under a redraw scope.
  This is not a constant-time memory-image restore. Its cost still needs measuring.
- IconLayoutEngine::SaveDataModelToPropertyBag serializes its native model into a
  stream and writes the IconLayouts property, with IconNameVersion metadata.
- IconLayoutEngine::ReadStreamFromPropertyBag reads the same property and passes
  its stream into the model's native loader.

The four relevant functions also resolve in the previously archived VM image,
shell32 10.0.19041.6456; their addresses differ. Their existence on these two
builds is evidence for a native serialization path, not a public callable ABI,
not evidence that FS's free-folder host uses that model, and not a measured gain.
No private call is introduced or claimed validated by this investigation.

The reasonable next private prototype is to identify the actual model/legacy
state used by free folders and its ownership, then reuse a native load/apply
transaction with exact coordinate/identity/focus checks. The same question must
be tested independently in Tiles. A raw memory snapshot containing live COM
pointers, heap addresses or stale item indexes is not an acceptable persistent
format. An optional accelerator would retain the current public restoration
path, qualify the actual loaded implementation, and invalidate cached metadata
when the relevant Shell binary changes. Absence alone must only remove gains.
A blob's existence does not establish that safe adoption is already possible.
