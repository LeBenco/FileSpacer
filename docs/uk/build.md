# Збирання FileSpacer у Windows x64

FileSpacer призначено для Windows 10 або новішої, x64. Використовує MSVC/NMAKE й NSIS, не CMake. Команди збирання й тестів виконуйте в CMD у корені. Карта коду: [огляд розробника](technical/README.md).

<a id="dependencies"></a>

## Залежності

- Visual Studio 2022 Build Tools із MSVC, ATL і Windows SDK. Засіб запуску очікує `%ProgramFiles(x86)%\Microsoft Visual Studio\2022\BuildTools`.
- Inkscape, зазвичай `C:\Program Files\Inkscape\bin\inkscape.com`.
- Python із Pillow з Windows-дистрибутива Inkscape; збирання використовує сусідній `python.exe`. `ICON_PYTHON` вибирає іншу інсталяцію.
- ImageMagick із `magick` у PATH.
- NSIS, зазвичай `%ProgramFiles(x86)%\NSIS\makensis.exe`, для пакування.
- Node.js 22+, Ruby 3.3 і Bundler для офлайнової довідки; див. [збирання сайту й довідки](website/README.md#shared-website-and-offline-builds).

<a id="build-and-clean"></a>

## Збирання й очищення

Закрийте FileSpacer перед збиранням, потім виконайте:

```cmd
build.cmd debug
build.cmd release
build.cmd installer
```

`build.cmd` ініціалізує MSVC x64 через `vcvars64.bat` і запускає NMAKE. Debug використовує `FILESPACER_DEBUG`, `/MTd` і консольну підсистему. Release — `/O2`, `/MT` і підсистему Windows. C++ використовує `/W4` та C++14. Нові одиниці додавайте до відповідного `OBJECTS` у `Makefile`.

| Результат | Використання |
| --- | --- |
| `build\debug\FileSpacer.exe` | Розробка й регресійні тести. |
| `build\release\FileSpacer.exe` | Програма випуску. |
| `FileSpacerFolder.dll` | Нативний постачальник змішаного сортування біля програми; зберігайте разом. |
| `build\FileSpacer-install.exe` | Інсталятор для поширення. Пакування його не запускає. |

Щоб указати нестандартні розташування засобів:

```cmd
set "INKSCAPE=D:\Tools\Inkscape\bin\inkscape.com"
set "MAKENSIS=D:\Tools\NSIS\makensis.exe"
build.cmd installer
```

Незмінене збирання має залишити виконуваний файл актуальним. Ціль інсталятора завжди перепаковує артефакти Release.

```cmd
build.cmd clean
```

Clean видаляє результати Debug/Release, згенерований ICO й інсталятор, зберігаючи джерела та дані користувача. Наступне збирання відтворить піктограму.

<a id="generated-artwork"></a>

## Генерована графіка

`generate-icon.py` створює десять кадрів `src\res\FileSpacer.ico` із SVG та оптичних зразків малих розмірів. Для 16–48 пкс папка малюється на піксельній сітці, багатокутники тесеракта передискретизуються й зменшуються фільтром Box. Inkscape формує 64–256 пкс. ImageMagick пакує; генератор перевіряє декодоване RGBA перед атомарною заміною ICO. NumPy не потрібен.

Визначальними є 2D-багатокутники SVG; генератор не перераховує проєкцію з метаданих 4D/камери. Зміна силуету чи координат 212 × 212 також потребує оновлення `FOLDER_MASTERS` / `draw_folder`. Синхронізуйте [favicon 16 пкс](website/README.md).

Пакування запускає `generate-installer-assets.py` для позначки завантаження, бічних панелей, DLL ресурсів і журналу UTF-16. Результати — у `build\installer-assets`, поза Git. `installer\wizard-ui.rc` задає спільний макет. x86 `WizardBitmap.dll` масштабує панелі через GDI+ із резервним завантажувачем NSIS. Розпаковується лише до тимчасового каталогу модулів NSIS. Перевірка Debug із командного рядка розробника x64:

```cmd
nmake /f Makefile CFG=Debug installer-bitmap
```

<a id="sqlite"></a>

## SQLite

Незмінений об’єднаний код у `third_party\sqlite` збирається окремо як C і компонується статично. DLL SQLite, CLI чи завантаження під час збирання не потрібні. Див. [походження й параметри](https://github.com/LeBenco/FileSpacer/blob/main/third_party/sqlite/README.txt).

SQLite використовує `/W3`, `_CRT_SECURE_NO_WARNINGS`, `SQLITE_OMIT_LOAD_EXTENSION` і `SQLITE_DQS=0`, зберігаючи типову потокобезпечність і статичну бібліотеку виконання. Release компонується з `/OPT:REF /OPT:ICF`. У рядку розробника:

```cmd
dumpbin /dependents build\release\FileSpacer.exe
```

Залежності від `sqlite3.dll` не має бути; системні DLL Windows залишаються потрібними.

<a id="offline-help-and-installer-contracts"></a>

## Офлайнова довідка й контракти інсталятора

Інсталятор пакує каталог `help`, перевіряє відбиток джерел/хеші та відтворює відсутню, застарілу чи пошкоджену копію. Node.js має бути в PATH (`NODE` може перевизначити); Ruby/Bundler потрібні лише для генерації. [Робочий процес випуску](https://github.com/LeBenco/FileSpacer/blob/main/.github/workflows/release.yml) може передати перевірену Linux-довідку до пакування Windows з того самого перевіреного коміту. Для читання потрібен лише браузер без сервера чи мережі.

Інсталятор починає як `asInvoker`. Інсталяція для всіх запускає підвищений робочий процес через `runas` лише на початку. Ініціатор зберігає каталог, мову й компоненти, очікує код виходу та застосовує особисті зіставлення до початкового користувача. Робочий процес не змінює особистий типовий менеджер адміністратора. Видалення для всіх також потребує підвищення. Скасування зберігає контракт кодів оновлювача.

`install-info.ini` записує область, мову й компоненти. У `[Components]` значення `StartMenu`, `ContextMenu`, `DefaultFileManager` — `0` або `1`. Оновлення відновлюють вибір; тихі зберігають ефективне типове зіставлення, навіть змінене після інсталяції. Типовий менеджер потребує компонента контекстного меню.

Посередник оновлення визначає область із метаданих біля запущеної програми. Резервний реєстр має відповідати точному каталогу лише в одній області. Після успіху всіх секцій інсталятор пише UTF-16 `/UpdateResult=` з `[Installation]`, `Mode`, `Executable`, `Complete=1`. Посередник перевіряє програму й область перед відновленням вікон. Скасування/помилка повертає оригінал; хибний успіх зберігає сеанс і повідомляє помилку. Очищення старих посередників не видаляє очікувані сеанси. Межу перевіряє `11-session-maj`.

Журнали — `%TEMP%\FileSpacer-install.log` і `%TEMP%\FileSpacer-install-machine.log` для робочого процесу. `/Log="C:\path\setup.log"` змінює початковий журнал. Кожен запуск замінює свій файл. Код файлових операцій 5 — категорія інсталятора, не номер помилки Windows. Зберігайте першу помилку, виняток/стек очищення й коди команд; журналювання не змінює результату операції.

Збирання NSIS перевіряє пакування, а не справжню інсталяцію, UAC, оновлення чи видалення. Перевіряйте змінені інстальовані шляхи окремо.

<a id="releases"></a>

## Випуски

Процес випуску запускається тегом `vX.Y.Z` або вручну для наявного тега. Спочатку повторно використовується [робочий процес регресії програми](https://github.com/LeBenco/FileSpacer/blob/main/.github/workflows/regression.yml), який має успішно завершитися, потім довідка й NSIS збираються з вибраного й підтвердженого SHA. Версія звіряється з тегом, а `FileSpacer-X.Y.Z-install.exe` і `FileSpacer-update.txt` публікуються в GitHub Releases. Звичайний push гілки не публікує інсталятор. Для випуску достатньо автоматичного токена GitHub.

Відповідний результат PASS для тотожних вхідних даних програми й тестів можна використати повторно без нового запуску; див. [кеш результатів регресії](tests/regression/README.md#run-on-github).

Поширення необов’язкове: типово випуск публікується лише на GitHub. Якщо вибрано WinGet, окреме завдання подає інсталятор; потрібен секрет `WINGET_TOKEN`, а помилка не скасовує випуск. Див. [поширення WinGet](winget.md). Канал `chocolatey` використовує `CHOCO_API_KEY`.

Перед публікацією оновіть обидві версії в `src/resource.h`, додайте секцію `CHANGELOG.md` й закомітьте потрібні зміни. У Git Bash підставте версію:

```bash
bash release.sh X.Y.Z
bash release.sh X.Y.Z --distribute winget
bash release.sh X.Y.Z --distribute chocolatey
bash release.sh X.Y.Z --distribute winget --distribute chocolatey
```

Без параметрів канали не вибрано; `--distribute none` указує це явно й не поєднується з каналом. Повторюйте параметр для кількох каналів; дублікати вилучаються. Анотація тега зберігає вибір як `FileSpacer-Distribution: winget,chocolatey` або `none`; відсутність цього поля також вимикає автоматичне поширення.

Сценарій потребує чистого дерева, перевіряє віддалену гілку/тег, показує зміни й канали та запитує підтвердження перед push `main` і анотованого тега. Потім перевірте процес і обидва файли випуску. Підсумки помилок і журнали лишаються артефактами процесу.

Наявний випуск можна подати пізніше через **Distribute FileSpacer (channel=winget)** та/або **Distribute FileSpacer (channel=chocolatey)**, вибравши `main` і опублікований тег. Ручний запуск вибирає канал незалежно від початкового рішення та використовує той самий інсталятор і SHA-256. Приклад: `gh workflow run distribution.yml --ref main -f channel=winget -f tag=vX.Y.Z` або та сама команда з `-f channel=chocolatey`. Не перезапускайте для цього генерацію випуску: вона може замінити інсталятор і зробити контрольні суми каталогів недійсними.

<a id="tests"></a>

## Тести

[Посібник регресії](tests/regression/README.md) описує той самий набір тестів програми на локальному робочому столі Windows, у Hyper-V та через GitHub Actions, зокрема вибір випадків, передумови й тлумачення звітів. Наприклад:

```cmd
tests.cmd -Category Internal
tests.cmd -VM AgentWin10 -Category UI -Pattern "16-redimensionnement-alt\03-*"
```

Запускайте відповідні тести під час розробки. Тести використовують Debug та ізольовані дані; ніколи не видаляйте робочу базу для підготовки. Перед зміною відновлення чи життєвого циклу читайте [архітектуру оболонки](native-shell-view.md).
